# AXIS v1.3.0 — Ideas & Roadmap

**v1.3.0 wird BIG.**

v1.1.0 hat AXIS die Sprache gegeben. v1.2.0 hat den Compiler schnell gemacht (14 Optimizer-Passes, GCC -O0 geschlagen). v1.3.0 macht AXIS zu einer **echten Plattform** — neue IR, Multi-File, Standard-Libraries und Performance-Kontrolle.

---

## 1. Zwei getrennte IRs — Script-IR & Compile-IR

Die aktuelle IRGen ist funktional, aber **extrem umständlich für Performance**. Für v1.3.0 wird die IR-Generation von Grund auf neu geschrieben — und zwar **doppelt**: eine leichtgewichtige IR für Script-Modus, eine aggressive IR für Compile-Modus.

**Problem:** Eine einzige IR kann nicht gleichzeitig "blitzschnell kompilieren" und "GCC -O3 schlagen". Das sind zwei fundamental verschiedene Ziele. Die aktuelle IR ist zu nah am AST und produziert massiv redundante Instruktionen — der Optimizer muss zu viel aufräumen.

**Lösung: Zwei IRs mit völlig verschiedenen Design-Zielen.**

---

### 1a. Script-IR — Schnelligkeit über alles

Für `axis run program.axis` — der interaktive Modus, in dem die Compile-Time entscheidend ist.

**Design-Ziele:**

- **Minimale Compile-Time** — so wenig Transformationen wie möglich zwischen AST und Maschinencode
- **Einfacher Aufbau** — Stack-basiert, nah am AST, kein SSA nötig
- **Nur Basic-Opts die nichts kosten:** Constant Folding, Dead Code Elimination, einfache Copy Propagation
- Kein aufwändiges Register Allocation — einfaches Schema reicht
- Kein Inlining, kein Loop Unrolling, keine Dataflow-Analyse

**Philosophie:** Gut genug, um brauchbar zu laufen. Die Priorität ist: Nutzer tippt Code, drückt Enter, sieht sofort das Ergebnis. Jede Millisekunde Compile-Time zählt.

---

### 1b. Compile-IR — GCC/LLVM angreifen

Für `axis build program.axis` — der Produktions-Modus, in dem die Laufzeit-Performance zählt.

**Design-Ziele:**

- **SSA-Form** (Static Single Assignment) als Basis
- **PHI-Nodes** für saubere Kontrollfluss-Merges
- **IR-Level Typinformationen** für bessere Optimierungsentscheidungen
- Designed für **aggressive Optimierungen**: Loop Unrolling, Strength Reduction, Global Value Numbering, Alias Analysis, Auto-Vectorization
- Bessere Registernutzung direkt aus der IR heraus
- Weniger unnötige Loads/Stores von Anfang an

**Ziel:** Nicht nur GCC `-O0` schlagen (das können wir schon), sondern langfristig **`-O2` oder sogar `-O3`** und **LLVM `-O3`** in den relevanten Benchmarks angreifen. Die Compile-Time darf hier ruhig höher sein — was zählt ist der generierte Code.

**Philosophie:** Wenn ein Nutzer `axis build` sagt, will er die schnellstmögliche Binary. Ob das 2 Sekunden oder 10 Sekunden dauert, ist egal — solange das Ergebnis mit GCC/Clang mithalten kann.

## 2. Features aus den Release Notes (bereits geplant)

Diese Features sind in den [RELEASE_NOTES_v1.3.0.md](RELEASE_NOTES_v1.3.0.md) bereits dokumentiert:

### String-Variablen im Compile-Modus

- Deklaration & Zuweisung: `name: str = "hello"`
- Vergleich: `==`, `!=`
- Konkatenation: `+` Operator
- Funktionsparameter & Rückgabe als `str`
- String-Arrays: `names: (str; 5)`
- Implementierung: Pointer + Length auf dem Stack, Arena für Konkatenation

### Type Casting mit `copy ... as` / `update ... as`

- Widening (sign-extend / zero-extend)
- Narrowing (Truncation + Compiler-Warning)
- Kein `bool ↔ integer` — Compile Error
- Immer explizit, niemals implizit

### Compile-Time Constants

- `const MAX: i32 = 16` — Integer-Typen und `bool`
- Verwendbar als Array-Größen
- Können andere `const`-Werte referenzieren

### Labeled Loop Control

- `outer for i in range(0, 10):` + `stop outer` / `skip outer`
- Löst das Nested-Loop-Escape-Problem

### Verbesserte Fehlermeldungen

- Source-Context mit Caret-Markierung
- "Did you mean?"-Vorschläge
- Multi-Error-Collection (bis zu 10 Fehler)

## 3. Neue CLI-Befehle — Performance-Kontrolle

GCC-inspirierte Flags, die dem Nutzer Kontrolle über die Compiler-Performance geben:

```text
axis program.axis                    # Default (alle Optimierungen an)
axis program.axis -O0                # Keine Optimierungen (schnellste Compile-Time)
axis program.axis -O1                # Basis-Optimierungen (DCE, ConstFold, CopyProp)
axis program.axis -O2                # Alle aktuellen Optimierungen (Default)
axis program.axis -O3                # Aggressiv (Inlining-Limit höher, Loop Unrolling aggressiver)
axis program.axis -Os                # Size-Optimierung (minimale Binary-Größe)
```

**Weitere Flags:**

```text
axis program.axis --no-inline        # Inlining deaktivieren
axis program.axis --unroll-limit=N   # Loop-Unrolling-Limit setzen
axis program.axis --dump-ir          # IR nach stdout ausgeben (Debugging)
axis program.axis --dump-asm         # Generierten x64-Assembly ausgeben
axis program.axis --time             # Compile-Time pro Phase anzeigen
```

## 4. Multi-File Support

AXIS ist derzeit auf einzelne Dateien beschränkt. Multi-File macht AXIS skalierbar.

```axis
import "player.axis"
import "physics.axis"

player: Player
apply_gravity(update player)
```

**Design:**

- Kein Modul-System, kein Namespace-Overhead
- `import "datei.axis"` — inkludiert die Datei (Duplikate werden ignoriert)
- Funktionen und Types aus importierten Dateien sind direkt verfügbar
- Zirkuläre Imports werden erkannt und als Fehler gemeldet
- Relative Pfade zum aktuellen File

## 5. Standard-Libraries — Die Big Four

Vier mitgelieferte Libraries, die mit `import` geladen werden. Keine externen Dependencies — alles in AXCC eingebaut.

---

### 5.1 `import math`

**Ziel: NIEMALS muss irgendwer eine Mathe-Lib für AXIS entwerfen.**

Nicht nur Grundschul-Mathe wie Pythons `math`-Modul. Alles was man jemals braucht — von Trigonometrie bis Vektorrechnung — in einer einzigen Library. Das Äquivalent von `math` + `NumPy` + `SciPy` + `SymPy` in einem.

```axis
import math

# Trigonometrie
angle: f64 = math.sin(0.5)
hyp: f64 = math.hypot(3.0, 4.0)

# Matrizen
m: Matrix = math.mat_identity(4)
result: Matrix = math.mat_mul(m, rotation)

# Vektoren
v: Vec3 = math.vec3(1.0, 2.0, 3.0)
n: Vec3 = math.normalize(v)
d: f64 = math.dot(v, n)
c: Vec3 = math.cross(v, n)

# Graph Plotting
math.plot(x_data, y_data, "output.png")
math.histogram(values, bins: 20)

# Lineare Algebra
eigenvalues: (f64; N) = math.eigen(matrix)
inv: Matrix = math.inverse(matrix)
det: f64 = math.determinant(matrix)

# Statistik
mean: f64 = math.mean(data)
std: f64 = math.stddev(data)

# Komplexe Zahlen
z: Complex = math.complex(3.0, 4.0)
mag: f64 = math.abs(z)

# Numerische Integration
area: f64 = math.integrate(func_ptr, 0.0, 1.0)

# Und alles andere:
# - Fourier-Transformation
# - Interpolation & Kurvenanpassung
# - Differentialgleichungen
# - Polynome
# - Kombinatorik & Zahlentheorie
# - Koordinatentransformationen
# - Quaternionen
# - Zufallszahlen & Verteilungen
```

### 5.2 `import ui`

**Volle GUI- und Fensterkontrolle.** Nicht Pythons tkinter mit 90er-Jahre-Grafik, sondern modernes UI auf CSS-Level — ohne CSS zu kopieren.

```axis
import ui

window: Window = ui.create("Mein Programm", 800, 600)

# Layout
panel: Panel = ui.panel(window)
ui.background(panel, "#1e1e2e")
ui.padding(panel, 16)

# Widgets
btn: Button = ui.button(panel, "Klick mich")
ui.on_click(btn, handle_click)

label: Label = ui.label(panel, "Willkommen!")
ui.font_size(label, 24)
ui.color(label, "#cdd6f4")

input: TextInput = ui.text_input(panel, "Name eingeben...")

# Layout-Kontrolle
ui.row(panel, btn, label)         # Horizontal anordnen
ui.column(panel, input, btn)      # Vertikal anordnen
ui.center(panel)                  # Zentrieren

# Canvas / Custom Drawing
canvas: Canvas = ui.canvas(panel, 400, 300)
ui.draw_rect(canvas, 10, 10, 100, 50, "#89b4fa")
ui.draw_circle(canvas, 200, 150, 40, "#f38ba8")
ui.draw_text(canvas, 50, 50, "Hello!", 16)

# Event Loop
ui.run(window)
```

**Design-Philosophie:**

- Modern aussehend out-of-the-box (kein Retro-Look)
- Deklaratives Layout ohne Markup-Sprache
- Kein CSS, kein HTML, kein XML — alles ist AXIS-Code
- Styling über Funktionsaufrufe statt Stylesheet-Dateien
- Muss noch genauer designt werden (Rendering-Backend, Plattform-Support, etc.)

### 5.3 `import inlcode`

**Inline Code** — Fremde Sprachen direkt in AXIS einbetten. Support für **C, C++, Assembly und Rust**.

**C und Assembly sind nativ eingebaut** — AXCC kann C-Code direkt kompilieren und Assembly direkt emittieren, keine externen Dependencies nötig.

**C++ und Rust brauchen einen externen Compiler.** Der Pfad wird über Konfiguration angegeben:

```axis
# Compiler-Pfade konfigurieren (am Anfang der Datei oder in axis.config)
inlcode.cpp.compiler: PATH = "C:/msys64/ucrt64/bin/g++.exe"
inlcode.rust.compiler: PATH = "C:/Users/marlo/.rustup/toolchains/stable/bin/rustc.exe"
```

```axis
import inlcode

# Inline C — nativ, kein externer Compiler nötig
result: i32 = inlcode.c("
    int x = 42;
    x * 2;
")

# Inline Assembly — nativ, direkt in den Output eingebettet
inlcode.asm("
    mov rax, 60
    xor rdi, rdi
    syscall
")

# Inline C++ — braucht g++/clang++ (siehe inlcode.cpp.compiler)
vec_sum: f64 = inlcode.cpp("
    std::vector<double> v = {1.0, 2.0, 3.0};
    double sum = 0;
    for (auto x : v) sum += x;
    sum;
")

# Inline Rust — braucht rustc (siehe inlcode.rust.compiler)
hash: u64 = inlcode.rust("
    use std::hash::{Hash, Hasher};
    use std::collections::hash_map::DefaultHasher;
    let mut hasher = DefaultHasher::new();
    42u64.hash(&mut hasher);
    hasher.finish()
")
```

Wenn `inlcode.cpp` oder `inlcode.rust` verwendet wird aber kein Compiler konfiguriert ist → **Compile Error** mit klarer Meldung welcher Pfad fehlt.

**Nutzen:**

- C und ASM direkt einbetten ohne Setup
- Zugriff auf C++-Libraries wenn g++/clang++ vorhanden
- Rust für Safety-kritische Abschnitte wenn rustc vorhanden
- Schrittweise Migration von/zu AXIS

### 5.4 `import performance`

**Alles was Performance betrifft** — mmap, SIMD, Multithreading und mehr. Nur verfügbar mit explizitem `import performance`.

```axis
import performance

# SIMD — Vektorisierte Operationen
a: simd.f32x8 = simd.load(data, 0)
b: simd.f32x8 = simd.load(data, 8)
c: simd.f32x8 = simd.add(a, b)
simd.store(result, 0, c)

# Memory Mapping
file: MMap = performance.mmap("large_dataset.bin")
value: i32 = performance.mmap_read_i32(file, offset)
performance.mmap_close(file)

# Multithreading
performance.parallel_for(0, 1000000, func process_chunk(start: i32, end: i32):
    for i in range(start, end):
        data[i] = data[i] * 2
)

thread: Thread = performance.spawn(func worker():
    # Background-Arbeit
    heavy_computation()
)
performance.join(thread)

# Mutex für shared state
lock: Mutex = performance.mutex()
performance.lock(lock)
shared_counter = shared_counter + 1
performance.unlock(lock)

# Atomics
counter: Atomic = performance.atomic(0)
performance.atomic_add(counter, 1)

# Prefetching
performance.prefetch(data, offset + 64)
```

**Auto-Optimierung (nur Compile-Modus):**

AXCC kann `mmap` und `simd` **optional auch automatisch** für dich einbauen — allerdings schlägt dann die Compile-Time massiv in die Höhe. Das funktioniert **ausschließlich im Compile-Modus** (`axis build`):

```text
axis build program.axis --auto-simd         # Compiler vektorisiert automatisch wo möglich
axis build program.axis --auto-mmap         # Compiler nutzt mmap für große Datei-I/O
axis build program.axis --auto-simd --auto-mmap   # Beides — langsame Compile-Time
```

**Im Script-Modus** (`axis run`) widerspricht Auto-Performance dem Kern-Prinzip von schneller Compile-Time. Wenn du es trotzdem willst, gibt's eine Warnung + expliziter Override:

```text
axis run program.axis --auto-simd
# ⚠ Warning: --auto-simd drastically increases compile time.
#   This contradicts script mode's fast-compile philosophy.
#   Use --force-auto-perf to proceed anyway.

axis run program.axis --auto-simd --force-auto-perf   # OK, aber langsam
```

**Multithreading ist NICHT automatisch.** Es gibt kein `--auto-threads`. Multithreading erfordert immer expliziten Code über `import performance` mit einem ausgeklügelten System für Thread-Safety (Mutex, Atomics, `parallel_for` mit klaren Ownership-Regeln). Der Compiler wird dich niemals heimlich multi-threaded machen.

## Design-Philosophie: AXCC ist kein Koloss

AXCC wird nicht gebaut wie GCC oder LLVM — riesige Codebases mit Millionen Zeilen, die mit dem Holzhammer auf jedes Problem einschlagen. AXCC ist **von Grund auf smart**. Die Architektur selbst ist der Vorteil, nicht die Anzahl der Optimierungspässe.

### Grundarchitektur als Waffe

Was AXCC von Anfang an hat, was GCC/LLVM sich mühsam erkämpfen müssen:

- **Kein Pointer-Aliasing** — AXIS hat keine Pointer. Jede Variable ist eindeutig. GCC braucht `-fstrict-aliasing` und `restrict`-Hints und rät trotzdem oft falsch. AXCC weiß es einfach.
- **Value Semantics** — alles ist Wert, nichts ist Referenz. Perfekte Mutation-Analyse geschenkt, ohne aufwändige Escape-Analysis.
- **Whole-Program View** — AXCC sieht immer das komplette Programm. Keine separaten Translation Units, kein Link-Time-Raten. Jeder Call ist statisch auflösbar.
- **Kein dynamisches Dispatch** — keine virtuellen Methoden, keine Function Pointers, kein vtable-Overhead. Dead Code Elimination ist trivial.

Das sind keine Features die wir implementieren müssen — das sind Features die AXIS als Sprache **uns schenkt**.

### Smart Multi-File

`import "datei.axis"` ist kein dummes `#include`. AXCC erkennt Duplikate, löst Abhängigkeiten auf, und baut den Dependency-Graph einmal korrekt auf. Kein Header-Guard-Chaos, keine Include-Order-Bugs, keine Rebuild-Kaskaden weil sich ein Header geändert hat.

Jede importierte Datei wird **einmal** geparst, **einmal** analysiert, und ihre Symbole stehen sofort zur Verfügung. AXCC weiß zu jedem Zeitpunkt exakt, welche Datei welche Symbole exportiert und wer was braucht.

### Smart Native Libraries

`import math` lädt nicht die gesamte Math-Library in dein Binary. AXCC macht **Library-Level Tree-Shaking auf IR-Ebene**:

- Der Compiler weiß exakt, welche Funktionen aufgerufen werden — statisch, zur Compile-Time
- Unbenutzter Library-Code wird **vor** der Code-Generierung eliminiert — nicht hinterher per Linker
- Transitiv: Wenn `fourier()` intern `sin()` und `cos()` braucht, kommen die mit rein — aber `matrix_multiply()` nicht, wenn niemand es aufruft
- Das gilt für alle Standard-Libraries: `math`, `performance`, `inlcode`, `ui`

**Ergebnis:** Ein Binary mit `import math` aber nur `fourier()`-Nutzung ist kaum größer als ein Binary ohne `import math`.

### Das Anti-Pattern: Was AXCC NICHT ist

AXCC ist **nicht**:

- Ein Compiler der 200 Optimierungspässe braucht, weil seine IR so schlecht ist dass der Optimizer alles reparieren muss
- Ein Compiler der jede C-Altlast mitschleppen muss (Trigraphs, `volatile`, Bit-Fields mit Implementation-Defined Behavior)
- Ein Compiler der 15 Millionen Zeilen Code braucht um "Hello World" zu kompilieren
- Ein Compiler der über Pointer-Aliasing raten muss weil die Sprache es erlaubt

AXCC ist ein **präzises Werkzeug** — wenig Code, klare Architektur, ein Sprachdesign das dem Compiler in die Hände spielt statt gegen ihn zu arbeiten.

---

## Explicitly NOT (bleibt draußen)

- **Methods auf Fields** — AXIS ist value-oriented, keine versteckten `this`-Pointer
- **Classes / Inheritance** — kein OOP
- **Garbage Collector** — AXIS ist kompiliert, stack-basiert, deterministisch
- **Generics / Templates** — zu komplex für den Nutzen, AXIS bleibt einfach
- **Exceptions** — explizites Error-Handling über Rückgabewerte

## Prioritierung

| Prio | Feature | Aufwand | Impact |
| --- | --- | --- | --- |
| 1 | Script-IR (leichtgewichtig, schnelle Compile-Time) | Groß | Fundament Script-Modus |
| 1 | Compile-IR (SSA, aggressiv optimierbar) | Sehr groß | Fundament Compile-Modus |
| 2 | Release-Notes Features (Strings, Casting, const, Labels) | Groß | Sprache praktisch machen |

| 4 | Multi-File (`import`) | Groß | Skalierbarkeit |
| 5 | `import math` | Sehr groß | Killer-Feature |
| 6 | `import performance` (mmap, SIMD, Threads) | Sehr groß | Performance-Plattform |
| 7 | `import inlcode` (C, C++, ASM, Rust) | Groß | Interoperabilität |
| 8 | `import ui` | Sehr groß | GUI-Plattform |
